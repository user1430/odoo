01

五分钟看懂这套系统

The Big Picture

这套东西到底解决了什么问题

一句话：让 AI 助手（WorkBuddy）安全地操作企业里的 Odoo 系统（查订单、查库存、查客户），而不需要把系统密码交给任何人。

四个角色（全部用微信生态打比方）

一句话说清

整件事你每天在微信里都在做：第三方 App 让你「微信扫码授权登录」——你没把微信密码给它，但它能拿到你的昵称头像。把「你」换成「AI」，把「第三方 App」换成「WorkBuddy」，把「微信」换成「企业系统」，就是这个 demo。

技术名词微信生态里的对应物干什么的
MCP 协议小程序标准 API微信小程序不管什么业务都用同一套 wx.* 接口；MCP 同理——AI 不管背后是 Odoo 还是别的系统，都用同一种方式调工具（本 demo 暴露 17 个工具）
企业连接器企业微信后台「添加应用」管理员在 WorkBuddy 企业后台登记一次「系统在哪、去哪授权」，之后全企业员工都能用
OAuth 授权微信扫码授权登录不把账号密码给第三方，只给一张限时、限范围的授权凭证（token）。人离职了、凭证泄露了，作废一张凭证就行
IdP 授权服务器微信开放平台的授权服务专门发凭证、验凭证的「认证中心」（本 demo 用开源 node-oidc-provider 自建，登录方式是手机号 + 模拟验证码）
odoo-mcp 资源服务器App 自己的业务后台真正干活的一方：收到请求先向认证中心核实凭证（introspection），有效才去 Odoo 取数

只用「微信授权登录」这一个听众已有的心智模型，不再引入第二个类比场景——听众要记的新概念只有一个：AI 也能走这套授权。

数据怎么流动

员工在 WorkBuddy 提问「查一下生产订单」 │ ▼ 企业连接器（平台自动带 token，员工无感知） │ HTTPS 443 ▼ ┌────────────── 云服务器（自备，公网入口） ──────────────┐ │ Caddy（统一入口，自动 HTTPS 证书） │ │ ├─ odoomcpdemo.duckdns.org → odoo-mcp │ │ └─ odoomcp.duckdns.org → odoo-idp │ │ │ │ odoo-mcp：验凭证（问 IdP introspection） │ │ └─ 有效 → 经 SSH 隧道回讲师本机 Odoo 取数 │ │ odoo-idp：发凭证 / 验凭证（认证中心） │ └────────────────────────────────────────────────────────┘ │ SSH 反向隧道 ▼ 讲师本机 Odoo 18（demo 库，制造/CRM 演示数据）
为什么要画这张图给听众看听众只需记住三个层次：谁在用（员工/AI）→ 谁在管权限（连接器 + 认证中心）→ 谁在干活（odoo-mcp + Odoo）。所有技术细节都挂在这三层上讲，不会迷路。

重新启动演示（提示词一键拉起）

Restart Runbook

云端三个服务（odoo-mcp / odoo-idp / caddy）由 systemd 托管，服务器不关机就一直活着。要恢复的只有：本机 Odoo、SSH 反向隧道，外加确认云端健康。这些全部可以交给 CodeBuddy 做——复制下面这条提示词，在本工作区（CodeBuddy）里直接发给它：

PROMPT · 演示环境一键恢复 
帮我恢复 Odoo MCP 演示环境。按顺序执行，每步报告结果，任何一步失败先自行排查修复并说明原因，不要改动任何配置文件：

1. 检查本机 Odoo 是否可访问（http://127.0.0.1:8069，demo 库）。若未运行：先确认 Rancher Desktop 已启动，再到 Odoo docker-compose 项目目录启动它，等待 Web 可访问。
2. 执行 odoo_mcp_server/ssh-tunnel-start.sh 启动 SSH 反向隧道，并用 pgrep 确认进程存活。
3. 检查云端三个服务 odoo-mcp、odoo-idp、caddy 均为 active (running)，不是则 restart。
4. 三项自检：
   - curl -i https://odoomcpdemo.duckdns.org/mcp 应返回 401 且带 WWW-Authenticate 头
   - curl https://odoomcpdemo.duckdns.org/.well-known/oauth-protected-resource/mcp 应返回 200 JSON
   - 在云端执行 curl -s http://127.0.0.1:7069/web/login 应返回 Odoo 登录页 HTML
5. 全部通过后，输出一份「演示就绪报告」：各组件状态 + 我接下来在 WorkBuddy 里该点哪里。
⚑ 需要一次性配置 / 授权的步骤（仅这两处）
  • 第 1、2 步：本机已安装 Rancher Desktop、Odoo compose 项目在本机磁盘——装一次，之后提示词即可驱动；另需在 ~/.zshrc 加一行 export ODOO_DEMO_SERVER=<你的服务器地址>（隧道脚本从该变量读地址，一次性）。WorkBuddy 侧若无本地终端权限，前两步请在 CodeBuddy 里跑。
  • 第 3、4 步（云端操作）：二选一 —— ① CodeBuddy 的 Lighthouse 集成（execute_command，首次使用需登录授权，之后agent 可直接在服务器上执行命令）；② 本机 ~/.ssh 已配好免密登录云服务器的密钥。其余所有步骤（本机进程、隧道、公网 curl）无需任何特殊授权。

提示词背后发生了什么（你心里有数即可）

提示词步骤实际动作为什么必须按这个顺序
1. Odoodocker-compose 起 Odoo 18（demo 库，admin/admin）它是数据源。数据源没起，后面全通也只是「门开了、仓库是空的」
2. 反向隧道云端 7069 → 本机 8069（密钥 ~/.ssh/odoo_tunnel_ed25519）云端 odoo-mcp 与本机 Odoo 之间唯一的桥；办公网已放行 22 端口
3. 云端服务systemctl status / restart正常开机自启，这步只是确认，30 秒挡住 80% 现场翻车
4. 自检三发 curl分别验证三层：门（MCP 入口）、路标（OAuth 发现）、桥（数据隧道）

演示前 10 分钟人工检查表

  • 提示词跑完且「演示就绪报告」全绿任何黄灯都先解决，别带病上场
  • WorkBuddy 里实测一次连接器 enterprise_ruixin_test_demo 调 odoo_ping 返回 connected；再自然语言问一句「查一下生产订单列表」——观众只认这一步
  • 授权登录链路演练一次手机号 + 模拟验证码（验证码直接回显在登录页，纯演示不代表真实身份）
  • 开一个无痕窗口备用授权页若反复回弹，九成是浏览器 cookie 卡死（第 5 章 3 号坑），无痕立刻恢复
  • 网络兜底办公网封 8080 出方向；演示走公网 443 不受影响。网络不稳时手机热点兜底

现场翻车的三个典型症状与急救

症状最可能原因急救

03

开发过程与思路（含对话记录对照）

The Story

两天（2026-10-05 ～ 10-06），从「一把万能钥匙」演进到「标准授权制度」。每个阶段都给了「对照线索」：回你的 CodeBuddy 对话记录里搜关键词，就能看到当时真实的排查过程——讲到哪段不确定，现场搜给听众看，比任何转述都有说服力。

起点 · DAY 1 上午

静态 Token 版：能跑，但像一把永不换的万能钥匙

问题驱动：最初所有客户端共用同一个写死的 Bearer Token。谁拿到谁就是"管理员"，泄露无法收场，离职无法回收，审计无法区分人。企业场景下这不可接受——这就是整个改造的动机。
对话检索词 「静态 token」「MCP_AUTH_TOKEN」 · OpenSpec（基线，无提案） · Commit odoo 基线 ec1a407
Change① · DAY 1

打通平台 OAuth：先证明"标准授权码流程"走得通

思路：先不改任何服务器代码，用一个最小客户端（codebuddyOauth）把「登录 → 授权 → 拿 token」全流程跑通。先验证链路，再动生产代码，把风险隔离在沙盒里。这一天连踩三坑（错端点、localhost 被拒、cookie 卡死），对应第 5 章 1～3 号坑。
对话检索词 「账号不存在」「redirect_uri 参数错误」「localhost」 · OpenSpec fix-oauth-endpoints · Commit codebuddyOauth 4153223 起
Change② · DAY 2 上午

给 MCP 服务器装上"验凭证闸机"

思路：在 odoo-mcp 前加鉴权中间件：收到请求先问 IdP「这张凭证有效吗」（userinfo/introspection），有效才放行，带正负缓存避免每次出网。灰度策略：静态与 OAuth 双通道并存（mode=both），旧客户端零影响，新链路慢慢切。
对话检索词 「auth mode=both」「scope=openid」「正负缓存」 · OpenSpec add-oauth-mcp-auth · Commit odoo 9bd9d30 → 2223822；codebuddyOauth 8068c3f
关键转折 · DAY 2 下午

平台 IdP 走不通，果断自建 IdP

决策点：平台侧的动态注册接口（DCR）对第三方一律 403，等于"认证中心不给外部系统办接入"。与其死等平台开口子，不如用成熟开源组件（node-oidc-provider）自己当认证中心，半天完成替换并公网化。教训：平台能力边界要早探测，别在设计依赖它之后才发现。
对话检索词 「Trusted Hosts」「DCR」「node-oidc-provider」 · 记录 retrospective.md 第 4 条；oauthDemo README e6ca5f4
规范落地 · DAY 2 下午

按 MCP 2025 规范补齐"凭证该发给谁"

思路：新版 MCP 客户端授权时必带 resource 参数（这张凭证只能用于哪个服务），IdP 要支持（RFC 8707）；而带 audience 的凭证 userinfo 验不了，资源服务器必须改用 introspection 验（RFC 7662）。规范不是负担，是别人替你踩过的坑。
对话检索词 「invalid_target」「resource indicator」 · 云端备份标记 *.bak-rfc8707
收官 · DAY 2 傍晚

连接器配通 → 销毁万能钥匙（OAuth-only）→ 文档三件套

收官动作：企业连接器配通（17 个工具可用）→ 观察期后删除静态通道（原值即焚、不留档）→ 上线 HTTPS 域名入口 → 补齐 deployment / reproduction / retrospective 三份文档。破坏性变更永远带三件套：快照、改前基线、秒级回滚位。
对话检索词 「MCP_AUTH_MODE=oauth」「remove-static-token」 · OpenSpec archive/2026-10-06-remove-static-token · Commit odoo 2543e5d → dc277da

贯穿始终的四条工程思路（这部分最值得讲）

  1. 问题驱动，而非技术驱动。每一步都对应一个真实痛点（钥匙失控 → 平台不开门 → 规范不兼容），听众能听懂痛点，就听得懂方案。
  2. 先沙盒验证，再动生产。授权码流程先在独立小项目跑通，确认端点、回调、scope 全部正确后才改资源服务器。
  3. 灰度与回滚是胆量的来源。双通道并存 + 快照 + 秒级回滚位，让"删静态 token"这种破坏性操作可以从容执行。
  4. AI 结对开发的全过程天然是教学素材。每一步的对话记录、OpenSpec 提案、commit 都在本地可查——讲课时直接检索原文，让听众看到"人和 AI 是怎么一步步把坑排掉的"，这是传统讲义给不了的真实感。

第 1 步起：一条提示词，AI 代跑

原则：不让学员手敲命令。学员在自己电脑上打开 CodeBuddy 或 WorkBuddy，把下面这段发给它——从拉代码、装环境到起服务、自检，全部由 AI 代跑，出错自己修（它会以仓库里的 docs/reproduction.md A 路径为准）：

PROMPT · 本地最小复现 
帮我从零开始在本机搭一套 Odoo MCP + OAuth 最小复现环境（目标路径见 odoo_mcp_server/docs/reproduction.md 的「A. 纯本地复现」）。按顺序执行，每步报告结果，出错自行排查修复并告诉我原因：

1. 获取代码：检查当前目录是否已有 odoo_mcp_server 和 oauthDemo 两个项目。
   - 没有 odoo_mcp_server：执行 git clone -b 18.0 https://github.com/user1430/odoo.git；
   - 没有 oauthDemo：找讲师要代码包并解压（它是 IdP，仓库暂未公开）；
   - 确认 odoo_mcp_server/docs/reproduction.md 存在，再往下走。
2. 准备基础环境：确认 Docker（Rancher Desktop 或 Docker Desktop）、Python 3.11+、Node.js 22+ 已就绪；缺什么告诉我安装方法，不要自行全局安装。
3. 启动本机 Odoo 18（docker-compose），确认 http://127.0.0.1:8069 可访问（demo 库，admin/admin）。
4. 启动 IdP：在 oauthDemo/server 下 npm install；复制 .env.example 为 .env 并按文档表格填值——ISSUER=http://localhost:3000，DEMO_ECHO_SMS_CODE=true，运行 node scripts/gen-jwks.mjs 生成 JWKS_JSON 写入，CLIENT_SECRET 等密钥生成随机串填入（告诉我变量名即可，不要打印具体值）；然后 npm start（127.0.0.1:3000）。
5. 启动 odoo-mcp：在 odoo_mcp_server 创建 venv 并 pip install -e .，按文档 A.3 的环境变量以 OAuth 模式启动在 8080，introspection 指向 127.0.0.1:3000，client secret 与 IdP .env 保持一致。启动日志应出现 auth mode=oauth。
6. 自检：curl -i http://127.0.0.1:8080/mcp 应返回 401 且带 WWW-Authenticate；well-known 端点应返回 200。
7. 最后教我手动体验授权流程：打开 IdP 自测页 /client 用手机号+模拟验证码登录授权，拿到 token 后用 curl 带 token 调 /mcp 验证 initialize 200。把这三步的操作截图级说明写给我。
⚑ 提示词之外、必须人工的环节（只有两类）
  • 界面操作：WorkBuddy 企业后台创建 oauth2_code 连接器（填 MCP URL、授权/令牌端点、Scopes openid profile email、User Info Name Path name）——这一步必须在浏览器里点，也是教学的核心演示时刻，建议讲师现场带着点一遍。
  • 授权动作本身：登录页输手机号 + 模拟验证码、点"同意授权"——必须人来点，这正是 OAuth「人授权、机器执行」的精髓，演示时务必保留。
教学法建议先让 AI 把环境跑通，再带学员在自测页手动走一遍「授权 → 拿凭证 → 调通」。亲手走过一遍后，"连接器"在他们眼里就不是黑盒，而是"把我刚才手动做的事，交给平台自动做"。

学员必背的三个"凡是"

  • 凡是文档里的端点，先 curl 实证再写代码——官方模板也会有错。
  • 凡是密钥，只进 .env，不进代码、不进文档示例、不进 git——本项目一天抓到过四处硬编码。
  • 凡是破坏性变更，先快照、留回滚位，再动手——胆量来自退路。
05

踩坑图鉴（按普适性排序）

Hall of Traps

每张卡标注频率：高频 · 人人会遇到 或 中频 · 特定场景。只保留对别人有复用价值的坑；只在本次项目出现过一次的低频坑已略去（完整 18 条见 docs/retrospective.md）。对照线索指向你的本地对话记录，讲课时可现场搜出原过程。

高频 · 平台接入

1 · 官方文档/模板里的端点可能是错的

症状：按模板配的授权端点，落到企业登录页报「账号不存在」，怎么改参数都没用。真相：模板地址并非真实授权服务，实际可用的是另一组端点。

任何文档/模板给的端点，先 curl 实证再写进代码。一小时实测胜过一天调试。
对照 对话 2026-10-05 · 检索「账号不存在」 · OpenSpec fix-oauth-endpoints
高频 · OAuth 必遇

2 · localhost 与 127.0.0.1 不是一回事

症状：回调地址填 localhost 被平台直接拒绝，改成 127.0.0.1 立刻通过。一字之差，卡一小时。

平台侧填回调一律用 127.0.0.1；同时规划好端口，避开本机已占用端口（当时 3000 被占，用了 3001）。
对照 对话 2026-10-05 · 检索「localhost」
高频 · 演示现场必背

3 · 「登录故障」其实是浏览器 cookie 卡死

症状：短信验证码提交后被弹回登录页、反复循环，怎么看都像平台挂了。真相：认证服务的会话 cookie 在当前浏览器卡死。换无痕窗口立刻恢复。

怀疑平台故障前，先用无痕窗口隔离浏览器状态；排查期间可用命令行方式（client_credentials + scope=openid）兜底验证端点。这是 OAuth 调试最常见的"灵异事件"，讲师必须预判。
对照 对话 2026-10-06 · 检索「无痕」「execution」
高频 · 凭据安全

4 · 密钥硬编码的四个藏身处

现场：一天抓到四处真实密钥——代码里的默认值、.env.example 填真值、README 的 curl 示例带真值、还有一个进了 git commit（最后 amend + gc 抹除并轮换）。

① 代码 fail-fast，不写默认值——没有默认值就没有泄露；② .env.example 和文档示例按"占位符"标准评审；③ 提交前 grep 已知密钥值，是最便宜的扫描；④ 本地仓库没有 remote 不代表可以入库，历史会跟着仓库走。
对照 retrospective.md 第 8 条 · 检索「amend」「轮换」 · 关联 memory：凭据不入库规则
中频 · 上域名时

5 · 域名一上，MCP 全部 421 Invalid Host header

症状：localhost 一切正常，换域名访问立刻 421。真相：FastMCP 默认开启 DNS-rebinding 保护，只认 loopback 的 Host 头。

不要关保护，用 Caddy 反代统一改写 Host 头（header_up Host 127.0.0.1:8080），零代码改动、保护仍在。安全默认值要先理解再绕行。
对照 对话 2026-10-06 · 检索「421」「header_up」
中频 · MCP OAuth 接入

6 · MCP OAuth 的规范是一个"套餐"，单点做会连环报错

症状：先报 invalid_target: resource indicator is missing（RFC 8707：客户端要求声明凭证用途）；修完后带 audience 的凭证又被 userinfo 拒（必须改用 introspection，RFC 7662）；401 若不带 WWW-Authenticate 挑战头，客户端连"去哪授权"都不知道（RFC 9728）。

把 9728（资源元数据）+ 8707（resource）+ 7662（introspection）+ 401 挑战头当一个套餐讲、一个套餐做，缺一块就会在下个环节爆雷。
对照 对话 2026-10-06 · 检索「invalid_target」「WWW-Authenticate」 · 云端备份 *.bak-rfc8707
中频 · 方案设计期

7 · 把平台能力边界的探测拖到了设计之后

症状：方案已按「用平台接口动态注册客户端」设计，实测发现该接口对第三方一律 403，此路不通。

依赖外部平台的关键能力，第一天就做可行性穿刺测试。这次发现得不算晚，半天切换到自建 IdP。
对照 对话 2026-10-06 · 检索「Trusted Hosts」「DCR」
中频 · 本地联调

8 · 测试打到了旧进程上

症状：改了配置重启服务，行为却像没改——残留的旧进程占着端口，新进程起不来，日志看着却像启动成功。

测试前 lsof -i :端口 确认端口归属；判断启动成功以真正 bind 成功的行为为准，不以启动日志为准。
对照 retrospective.md 第 14 条 · 检索「lsof」「bind」
已略去的低频坑「灰度指标无观测数据」「ss 输出误读」「caddy validate 副作用」「分片传输丢字符」等仅在本项目特定操作中出现一次，对学员复用价值低，已从正篇移除；讲师备课可翻 docs/retrospective.md 第 9～15 条备用。
06

演讲与录制建议

Presentation

推荐叙事线：效果 → 原理 → 故事 → 教学

0' – 3'
直接演示效果。打开 WorkBuddy，自然语言问「帮我查一下这周的生产订单」，等结果出来。此时一个字技术都不要讲。让听众先产生"我想要这个"。
3' – 8'
用第 1 章类比讲原理。「刚才发生的事，就跟你微信扫码授权登录一个 App 一模一样，只是主角换成了 AI」——全程只借这一个听众已有的心智模型，不引入第二个场景。
8' – 18'
讲开发故事（第 3 章时间线）。每讲到一段，现场在对话记录里搜出当时的原文给听众看——"这不是事后编的讲义，是当时真实的排查过程"。转折处（自建 IdP）是全篇最有戏剧性的点，放慢讲。
18' – 26'
踩坑图鉴精选（第 5 章）。只讲高频 4 张卡（约 8 分钟），中频一笔带过。核心信息：出问题先怀疑自己的环境，文档也可能是错的。
26' – 33'
教学环节（第 4 章）。现场把复现提示词发给 CodeBuddy，让 AI 跑、你解说——这本身就是"AI 结对开发"最好的广告。最后带听众在企业后台点一遍连接器创建，给「三个凡是」收尾。

对这类听众的五个表达技巧

  1. 术语零假设。第一次出现的缩写当场翻译：token = 授权凭证、IdP = 认证中心、introspection = 打电话回认证中心核实。
  2. 每屏只讲一件事。架构图分三层揭示，不要一次铺开全图。
  3. 用"翻车故事"代替"正确做法"开场。「我们卡了一小时，只因为把 127.0.0.1 写成了 localhost」比「请注意回调地址规范」有效十倍。
  4. 演示必须有 plan B。提前录好关键操作的成功录屏；现场只做能容忍失败的操作；授权登录前必开无痕窗口。
  5. 把凭据安全演给他们看。故意展示「密钥只在 .env、文档里全是占位符」，对渠道伙伴这是最有说服力的专业信号。

录制要点

  • 按章节分段录制（每段 5–10 分钟），比一镜到底更易补录复用；第 2、4 章适合纯操作录屏，第 3、5 章适合讲解 + 手册同屏。
  • 命令一律让 AI 跑（第 2、4 章提示词）或从备忘录粘贴，避免现场敲错；终端字体放大到 16px+。
  • 云端配置文件（override.conf、IdP .env）与服务器地址一律避开画面或打码；鉴权日志里 token 只有 sha256 前 8 位，是安全的可展示素材。
